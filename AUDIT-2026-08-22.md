## 1-partiya: HIGH/MEDIUM topilmalar (1-5)

### #1 — Boss-battle test sintaksis xatosi
**Fayl:** `tests/unit/config/boss-battle.test.ts:55`
`qo'shni` so'zidagi escape qilinmagan apostrof butun test faylini parse'dan to'xtatgan — 5 ta test umuman ishlamayotgan edi (eslint'ning yagona xatosi ham shu).
**Fix:** double-quote bilan qayta yozildi.

### #2 — Boss reward `RANK()` bug
**Fayl:** `server/modules/boss/boss.repository.ts`
Teng damage'da (masalan 50 user bir xil ballda) HAMMASI top-1 mukofotini olardi — cheksiz coin mint xavfi. Boss damage butun son (5 ballik qadam) bo'lgani uchun tie odatiy holat, chetki emas.
**Fix:** `RANK()` → `ROW_NUMBER() ... ORDER BY damage DESC, user_id`. Tie-holat integration testi qo'shildi.

### #3 — Coin ledger balansdan uzoqlashishi
**Fayl:** `server/modules/progress/progress.repository.ts`
`clientToken` optional (`ResultSchema`da) — yuborilmasa coin mint bo'lardi, lekin `coin_transactions`da qator qolmasdi. Balans va ledger summasi mos kelmay qolardi umrbod.
**Fix:** `COALESCE(clientToken, subjectId:questionId)` fallback ref — gate mexanizmi tufayli bu fallback ham dedup-safe.

### #4 — Consumable (premium-days) double-charge race
**Fayl:** `server/modules/coins/coins.repository.ts`
Durable buyumlar (`user_items` UNIQUE) claim-first bilan himoyalangan, lekin `premium-days` kabi consumable'da bunday claim yo'q edi — ikkita parallel so'rov bir xil `purchaseId` bilan kelsa ikkalasi ham debit qilishi mumkin edi.
**Fix:** `pg_advisory_xact_lock(userId+purchaseId)` — merch buyurtma pattern'iga o'xshash. Race integration testi qo'shildi.

### #5 — Leaderboard butun jadval scan qilardi
**Fayl:** `server/modules/leaderboard/leaderboard.repository.ts`
`FROM users LEFT JOIN progress ORDER BY COALESCE(...)` — COALESCE ifodasi `idx_progress_total_correct` index'idan foydalanishga to'sqinlik qilardi, har so'rov butun `users` jadvalini scan+sort qilardi.
**Fix:** `FROM progress INNER JOIN users`, xom column'lar bilan sort (index ishlaydi). Progress'siz user (bot invoice stub-user) reytingda ko'rinmaydi — bu qasddan (totalCorrect=0). Yangi `tests/integration/api/leaderboard.test.ts` qo'shildi.

## 2-partiya: qolgan topilmalar (6-17)

### #6 — Boss damage optimizatsiyasi — **QAYTARILDI (real bug topildi)**
`applyDamage`dagi 2 ta alohida SQL so'rovni (ensureActiveBoss + damage CTE) bittaga birlashtirmoqchi bo'ldim tezlik uchun. Bu `boss_battles` jadvaliga BIR WITH ichida IKKI marta yozish edi (sibling data-modifying CTE — INSERT + UPDATE). Postgres buni "unwise, natija kafolatlanmagan" deb hujjatlashtiradi. Integration test buzildi (`kill?.defeated` kutilgan `true` o'rniga `false` qaytardi) — real bug tasdiqlandi. **Xavfsiz eski holatga (2 round-trip) qaytarildi.**

### #7 — Merch cancel refund yo'qolishi — **YOLG'ON POZITIV**
Original taxmin: `credit` UPDATE 0 qator qaytarsa, refund jimgina o'tkazib yuboriladi. Qayta tekshirilganda: `merch_orders.user_id` va `user_coins.user_id` ikkalasi ham `users.id`ga CASCADE DELETE — user o'chirilsa ikkalasi birga yo'qoladi, `upd` hech narsa topmay to'g'ri `not_found` qaytaradi. **Fix kerak emas.**

### #8 — Click to'lov status tartibi
**Fayl:** `server/modules/payments/click.service.ts`
`error<0` tekshiruvi order status'dan OLDIN ishlab, eskirgan/replay xato webhook allaqachon 'completed' buyurtmani jimgina 'cancelled'ga tushirib qo'yishi mumkin edi.
Birinchi urinish (`if (order.status==='completed') return ALREADY_PAID` erta qaytish) noto'g'ri chiqdi — bu SAME-click_trans_id replay uchun kutilgan `SUCCESS`ni buzib, `ALREADY_PAID` qaytarardi (5 ta mavjud unit test yiqildi).
**To'g'ri fix:** `error<0` shartiga `&& order.status === 'pending'` qo'shildi — faqat hali ochiq buyurtmani bekor qiladi, 'completed'/'cancelled' holatlar pastdagi mavjud atomik claim/guard orqali o'z-o'zidan to'g'ri ishlaydi (replay → SUCCESS, boshqa trans_id → ALREADY_PAID).

### #9 — `BOT_WEBHOOK_SECRET` prod tekshiruvida yo'q edi
**Fayl:** `server/config/index.ts`, `server/api-entry/bot.ts`
Deploy vaqtida sezilmasdi, keyin har Telegram webhook update'i 500 qaytarardi (runtime'dagi mavjud fail-closed tekshiruv orqali).
**Fix (birinchi versiya):** `assertProdConfig()`ga qo'shildi + `bot.ts` boot'da chaqiradi.
**⚠️ Bu fix production incident'ga sabab bo'ldi — pastga qarang.**

### #10 — AI Tutor kvota tartibi
**Fayl:** `server/modules/tutor/tutor.router.ts`
Global kvota (`TUTOR_DAILY_GLOBAL_LIMIT`) user kvotasidan OLDIN tekshirilardi — `||` short-circuit tufayli, user o'z limitidan oshgan bo'lsa ham (agar global hali bo'sh bo'lsa) global byudjetdan bitta slot behuda sarflanardi.
**Fix:** tartib almashtirildi — user limiti avval.

### #11 — 10MB global body limit
**Fayl:** `server/app.ts`
`express.json({ limit: '10mb' })` GLOBAL edi — har bir endpoint (login, purchase, coins, tutor...) 120 req/min'da 10MB body qabul qilardi. Asossiz katta DoS sirti.
**Fix:** default `300kb`ga tushirildi (avatar upload ~100KB'dan katta joy qoldiradi); `admin/questions` (10mb) va `share/image` (5mb) route'lariga alohida katta limit path-based mount orqali berildi.

### #12 — `.env` fayldagi yetim qator
Local `.env`ning oxirgi qatorida `KEY=`siz yalang'och 64-hex qiymat bor (taxminan `CRON_SECRET=` yetishmayapti). **O'zim taxmin qilib tuzatmadim** — bu local sekret fayl, foydalanuvchiga qoldirildi.

### #13 — Telegram ID regex nomuvofiqligi
**Fayl:** `server/modules/share/share.router.ts`
`resolveTgChatId`da `/^\d{5,12}$/`, `octagon.ts`da `/^\d{1,20}$/` — kattaroq TG id'lar sekinroq DB fallback yo'liga tushib qolardi (ishlaydi, lekin keraksiz sekin). Performance nuance, correctness bug emas.
**Fix:** octagon.ts bilan sinxronlashtirildi.

### #14 — Auth allowlist prefix-match bug
**Fayl:** `server/middleware/auth.ts`
`isPublicAuthPost` `slice(0,3)/slice(0,4)` prefiks solishtirish qilardi — `POST /api/auth/phone/login/anything` (mavjud bo'lmagan chuqurroq yo'l) ham "public" deb belgilanardi. Amaliy ta'siri yo'q edi (Express baribir mos route topmay 404 qaytaradi), lekin allowlist niyatiga zid.
**Fix:** to'liq path exact-match'ga o'tkazildi.

### #15 — Hujjat nomuvofiqliklari
- `CLAUDE.md`: 2 ta cron yozilgan edi, aslida `vercel.json`da 4 tasi bor (daily-reminder, league-rollover, boss-rollover, cleanup-answer-tokens).
- `server/modules/cron/cron.router.ts`: izoh "02:00 UTC" deydi, haqiqiy schedule `0 3 * * *` (03:00).
**Fix:** ikkalasi ham to'g'irlandi.

### #16 — Seasonal window yil-wrap — **YOLG'ON POZITIV**
Original taxmin: `shared/shop-items.ts`da `from<=until` invariantini tekshiruvchi test yo'q, yil chegarasidan o'tuvchi mavsumiy oyna (masalan `12-25→01-05`) jimgina hech qachon ochilmasligi mumkin.
Qayta tekshirilganda: `tests/unit/config/shop-items.test.ts:77` da bu invariant ALLAQACHON tekshirilar ekan (`key(from) <= key(until)`). **Fix kerak emas**, original audit xatosi tan olindi.

### #17 — `requireSelf` yo'qligi ba'zi route'larda
**Fayllar:** `server/modules/progress/progress.router.ts`, `server/modules/users/users.router.ts`
`daily`/`achievements` router'lari `router.use(path, requireSelf)` explicit guard qo'llagan, `progress`/`users` esa faqat global `telegramAuth`dagi `USER_SEGMENTS` allowlist'ga tayangan (defense-in-depth bo'shlig'i — global check to'g'ri edi, lekin nomuvofiq patterns).
**Fix:** `router.use('/progress/:userId', requireSelf)`, `router.use('/profile/:userId', requireSelf)`, `router.use('/referrals/:userId', requireSelf)`, `router.use('/users/:userId', requireSelf)` qo'shildi. Avatar route'laridagi (PUT/DELETE) dublikat explicit `requireSelf` olib tashlandi (endi router-level guard orqali qamrab olinadi).

## Production incident: Render `yhq-websocket-server` qulashi

Birinchi fix-partiya push qilingandan keyin, foydalanuvchi Render'dagi WS servisi qizil ekanini aniqladi.

**Sabab:** #9-fix `assertProdConfig()`ga `BOT_WEBHOOK_SECRET` tekshiruvini qo'shgan edi. Bu funksiya **shared** — `server/index.ts` (Render standalone WS server) HAM boot'da chaqiradi. Lekin bu server Telegram webhookni UMUMAN ishlatmaydi (faqat `api/bot.ts`, alohida Vercel serverless function, ishlatadi), va `render.yaml`da `BOT_WEBHOOK_SECRET` sozlanmagan. Natijada Render WS server boot vaqtida `FATAL: required in production but missing: BOT_WEBHOOK_SECRET` bilan qulab tushdi.

**Fix (hotfix, `6f3ddaf`):**
- `BOT_WEBHOOK_SECRET` tekshiruvi `assertProdConfig()`dan olib tashlandi.
- Yangi, alohida `assertBotWebhookConfig()` funksiyasi qo'shildi — FAQAT `server/api-entry/bot.ts` chaqiradi.
- `server/index.ts` va `server/api-entry/index.ts` o'zgarishsiz qoldi (BOT_WEBHOOK_SECRET'ni tekshirmaydi).
- Test fayli (`tests/unit/config/prod-config.test.ts`) ikki alohida `describe` blokiga bo'lindi, yangi test qo'shildi: "BOT_WEBHOOK_SECRET assertProdConfig()ga ta'sir qilmaydi".
